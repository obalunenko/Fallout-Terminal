# Bug Report: Command behavior is not modeled as one exclusive variant

**Type**: Spec gap
**Severity**: Medium
**Feature**: 010-terminal-navigation
**Reported**: 2026-08-19
**Status**: Patched
**Patched**: 2026-08-19

## Description

`CommandContent` currently declares `state_change` and
`terminal_transition` as two independent `optional` protobuf fields. The
domain model mirrors that shape with two nullable pointers, and the master
command editor presents two checkboxes that uncheck each other in JavaScript.

The two behaviors are semantically exclusive and should be represented as one
command-behavior choice:

```proto
message CommandContent {
  string text = 1;
  oneof behavior {
    StateChangeConfig state_change = 2;
    TerminalTransitionConfig terminal_transition = 3;
  }
}
```

An ordinary command remains valid when the `oneof` is unset. Existing field
numbers and JSON names must remain stable. The master UI must expose one
exclusive choice—ordinary, state change, or terminal transition—instead of two
independent optional toggles.

The current backend validation rejects a command that contains both configs,
and the current UI normally unchecks the other checkbox. Those safeguards
prevent most invalid saves, but they do not encode the invariant in the
`CommandContent` type or communicate one coherent command mode in the editor.

## Root Cause Analysis

The original design optimized for an additive session-v1 extension: it added
`terminal_transition` beside the existing optional `state_change`, then
enforced mutual exclusion in `ValidateSession` and in two checkbox change
handlers. In proto3, each `optional` message field has independent presence;
the generated `oneof` markers are synthetic presence machinery and do not make
the two fields alternatives of one shared union. Consequently, code can still
construct a `CommandContent` containing both fields until later validation,
and the editor presents two apparently independent features even though only
one command behavior is valid.

The implementation therefore matches the current artifacts. The missing
requirement is to make exclusivity structural in the protobuf contract and
explicit as one choice in the authoring UI.
