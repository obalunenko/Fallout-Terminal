# Bug Report: Valid demo transition target is rejected as unknown

**Type**: Implementation drift
**Severity**: High
**Feature**: 010-terminal-navigation
**Reported**: 2026-08-19
**Status**: Patched
**Patched**: 2026-08-19

## Description

The game master cannot reliably configure and save a command in
`sessions/demo.json` as a transition from the first terminal to the second
terminal. Selecting `t_demo2` in the master application results in:

```text
terminals[0].root.children[4].terminalTransition.targetTerminalId references unknown terminal "t_demo2"
```

The source document is internally consistent: its terminal IDs are
`t_demo1` and `t_demo2`, and the affected command stores
`terminalTransition.targetTerminalId` as `t_demo2`. The current production
session decoder also accepts this document. Therefore the error is not caused
by a missing terminal in the authored JSON; the terminal collection used at
the failing master/native validation boundary does not match the complete
session document selected in the UI, or the application is validating a stale
copy of that document.

### Reproduction

1. Open `/Users/olegbalunenko/Desktop/Fallout-Terminal/sessions/demo.json` in
   the master application.
2. Edit `terminals[0].root.children[4]`.
3. Enable `terminalTransition` and select the second terminal (`t_demo2`).
4. Apply the command change and allow the master to save the session.
5. Observe the unknown-target validation error shown above.

### Expected result

The link to the existing second terminal is accepted, persisted, and remains
selected after the session is reopened.

### Actual result

The valid target is rejected as unknown, so the P1 authoring and persistence
flow cannot be completed with the bundled demo session.

## Root Cause Analysis

The durable document and lower-level validator are not the source of the
failure:

- `sessions/demo.json` contains both `t_demo1` and `t_demo2`.
- Its affected command points to `t_demo2`.
- `domain.ValidateSession` first gathers every terminal ID and only then checks
  transition references, so terminal order is not significant.
- The production bundled-demo decode test accepts the current file.

The defect was isolated at the master-to-native persistence boundary.
`desktopAPI` passed mutable session state into the asynchronous Wails
`SaveSession` call, allowing later UI or event mutations to change the terminal
set before serialization. The implementation now snapshots the complete
portable session synchronously before invoking `SaveSession`, preserving both
`t_demo1` and `t_demo2` while retaining strict rejection of missing and
self-referencing targets.

## Resolution and Verification

1. Added a regression spanning real demo open → master edit → Wails
   serialization → durable save → reopen.
2. Updated `desktopAPI` to snapshot the complete portable session before the
   asynchronous native save call.
3. Verified missing and self-referencing targets remain rejected.
4. Passed focused Go and browser tests, repository quality gates, production
   builds, and the packaged macOS `sessions/demo.json` persistence smoke.
