# Bug Report: Terminal transition pending state is shown as an overlay instead of a full-screen request

**Type**: Spec gap
**Severity**: High
**Feature**: `010-terminal-navigation`
**Reported**: 2026-08-19
**Status**: Patched
**Patched**: 2026-08-19

## Description

When the controlling player selects a command that leads to another terminal,
the source terminal menu remains visible and the player client shows a notice
overlay such as:

```text
ПЕРЕХОД В Взломанный терминал охраны ОЖИДАЕТ РЕШЕНИЯ МАСТЕРА
```

This differs from the established pending presentation for a state-changing
command that requires master approval.

### Reproduction

1. Start a broadcast with a controlling player and a command configured with
   `terminalTransition` to another terminal.
2. Select the transition command in the player client.
3. Leave the master decision dialog unresolved.
4. Observe that the current menu remains rendered while `#playerNotice` shows
   the transition-specific waiting message above it.

### Expected result

As soon as the authoritative transition request becomes pending, every player
view replaces the menu with the same full-screen record-style request surface
used by a pending state-changing command. Its body text is exactly:

```text
Выполняется запрос
```

The source terminal remains the authoritative active terminal, the route and
navigation state do not change, and all shared input remains blocked while the
full-screen request is visible. Approval replaces that screen with the target
terminal's normal initial presentation; rejection or closing the decision
dialog restores the unchanged source menu under the existing transition
semantics.

### Actual result

The source menu remains visible and the pending transition is represented only
by a separate `playerNotice` overlay. The authoritative lock is applied, but
the required full-screen request presentation is not rendered.

## Root Cause Analysis

The feature artifacts specify the pending state as data plus an input lock,
not as a screen contract. `T016` therefore implemented the narrow wording:
`client/client.js` formats `terminalNavigation.pending` as a transition-specific
message in `renderPlayerNotice()`, assigns it to `#playerNotice`, and adds the
`shared-input-pending` class. It does not route terminal navigation through the
full-screen record renderer used for `commandExecution.phase === 'pending'`,
where the body text is `Выполняется запрос`.

The tests preserve the same interpretation. The terminal-navigation journey
asserts that `#playerNotice` contains `ОЖИДАЕТ РЕШЕНИЯ МАСТЕРА`, including for
multi-player reconnect, while the state-changing-command journey explicitly
asserts the full-screen command surface and `Выполняется запрос`. Because the
`010` spec, plan, and tasks never stated that those presentations must match,
the overlay implementation and its tests could pass every recorded gate.

This is a presentation-only gap. The authoritative pending projection,
single-request behavior, active-terminal invariants, master resolution, route
mutation rules, and reconnect transport do not need to change.

## Resolution and Verification

1. Added **FR-029** and **SC-010** to require the shared full-screen record
   surface, exact `Выполняется запрос` text, hidden source menu, inert shared
   input, and controller/observer/reconnect convergence for direct pending.
2. Added failing regression task **T037** and reopened **T016**, **T027**,
   **T030**, **T031**, and **T036** for the player correction and all automated
   and packaged-runtime gates.
3. Routed direct `terminalNavigation.pending` through the existing record
   renderer without merging it with the command-execution protocol or making
   an optimistic terminal switch.
4. Verified controller, two observers, reconnect while pending, blocked
   `Back`/`Enter` and shared actions, approve/reject/close outcomes, the focused
   browser journey, repository quality gates, and the accepted packaged Wails
   runtime.
