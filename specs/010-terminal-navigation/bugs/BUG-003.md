# Bug Report: Return navigation pending state remains an overlay instead of a full-screen request

**Type**: Spec gap
**Severity**: High
**Feature**: `010-terminal-navigation`
**Reported**: 2026-08-19
**Status**: Patched
**Patched**: 2026-08-19

## Description

When the controlling player selects the root return action that leads to the
previous terminal, the current terminal remains visible and the player client
shows a notice overlay such as:

```text
ВОЗВРАТ В Терминал у входа в убежище ОЖИДАЕТ РЕШЕНИЯ МАСТЕРА
```

This differs from the established pending presentation for a state-changing
command and from the full-screen presentation already required for a direct
terminal transition.

### Reproduction

1. Start a broadcast and approve a direct transition from terminal A to
   terminal B so that the route contains a return point.
2. Complete or bypass any required hack and open terminal B's root list.
3. Select the return action that points to terminal A.
4. Leave the master decision dialog unresolved.
5. Observe that terminal B remains rendered while `#playerNotice` displays the
   return-specific waiting message above it.

### Expected result

As soon as the authoritative return request becomes pending, every connected
and reconnecting player view replaces the current terminal screen with the
same full-screen record-style request surface used by a pending state-changing
command. Its body text is exactly:

```text
Выполняется запрос
```

The current terminal remains authoritative and the route is not popped until
the master approves. `Back`, `Enter`, and all other shared actions remain
blocked. Approval replaces the request screen with the restored previous
terminal menu; rejection or closing the dialog restores the unchanged current
terminal root screen and its return action.

### Actual result

The current terminal screen remains visible and a return-specific
`playerNotice` overlay represents the pending request. The authoritative input
lock is active, but the required full-screen request presentation is not used.

## Root Cause Analysis

BUG-002 deliberately introduced a direct-transition-only presentation rule.
The implementation mirrors that wording: `client/client.js` uses
`isDirectTerminalNavigationPending()` to route only `direction === 'forward'`
through `renderTerminalNavigationPendingScreen()`. A pending `return` instead
falls through to `renderNormalScreen()`, while `renderPlayerNotice()` emits the
`ВОЗВРАТ ... ОЖИДАЕТ РЕШЕНИЯ МАСТЕРА` overlay.

The browser tests preserve the same split. The direct-transition regression
asserts the shared record surface, exact text, hidden menu, blocked input, and
multi-player reconnect behavior. The return journey verifies decision and
route semantics but does not assert the pending surface. Therefore the current
implementation and tests satisfy the existing artifacts; the desired return
presentation must first be encoded as a specification requirement.

## Resolution and Verification

1. Added **FR-030** and **SC-011** to extend the shared full-screen record
   surface, exact `Выполняется запрос` text, hidden current terminal and inert
   shared input to pending returns.
2. Added failing regression task **T038** and reopened **T016**, **T023**,
   **T027**, **T030**, **T031**, and **T036** for the player correction, return
   journey, multi-player convergence, and automated/native gates.
3. Generalized the terminal-navigation pending renderer to both directions and
   suppressed the notice overlay without popping the route or switching the
   authoritative terminal before approval.
4. Verified controller, two observers, reconnect while pending, inert
   `Back`/`Enter`, approval, unchanged root restoration after reject/close, the
   12-test focused browser journey, `make check`, and the accepted packaged
   Wails runtime delta.
