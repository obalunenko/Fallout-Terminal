# Bug Report: Ordinary commands bypass mandatory master approval

**Type**: Spec conflict
**Severity**: High
**Feature**: `010-terminal-navigation`
**Reported**: 2026-08-20
**Status**: Patched
**Patched**: 2026-08-20

## Description

Every player-selected command must require a master decision before the command produces any result, durable state change, or terminal transition. Approval must not depend on the command's authored behavior mode. In particular, an ordinary command whose `CommandContent.behavior` is unset must create the same single server-authoritative pending request as a state-changing command or terminal-transition command.

While any command is waiting for the master, the controller, observers, and reconnecting players must all see the same full-screen record-description presentation with the exact text «Выполняется запрос». The menu and other terminal surfaces must not remain visible, and `Back`, `Enter`, or another shared action must not bypass or dismiss the pending decision.

After approval, the command's mode still determines its effect:

- an ordinary command shows its authored result without creating durable command state or changing the active terminal;
- an initial state-changing command uses the existing persist-before-success transition;
- an already completed state-changing command shows its frozen result without executing or persisting it again;
- a terminal-transition command uses the existing atomic terminal/route transition.

Reject and close must preserve the pre-request canonical command, navigation, state, active terminal, and route. The bug concerns the universal approval gate and its shared waiting presentation; it does not make every command stateful or turn every command into a terminal transition.

The current artifacts intentionally define the opposite behavior for ordinary commands. Feature 010 preserves their existing behavior through FR-028, while inherited feature 009 explicitly requires commands without `stateChange` to execute without additional confirmation. The implementation and regression suite therefore permit exactly the approval bypass now reported as incorrect.

## Root Cause Analysis

Master approval was introduced incrementally as a property of specific effectful behaviors. Feature 009 created a pending lifecycle only for initial state-changing commands and deliberately retained a fast ordinary-command branch for backward compatibility. Feature 010 then added a separate pending lifecycle for terminal transitions and returns while preserving all non-transition behavior through FR-028. BUG-002 and BUG-003 unified how existing pending states render, but did not unify the condition that creates a pending request.

As a result, the system has shared visual primitives for requests that already require approval, but no universal approval boundary around command selection itself. The current implementation follows the artifacts: behavior-specific coordinator branches create pending state, while an unset ordinary behavior falls through to immediate live navigation/result handling. Regression tests explicitly protect that bypass, so an implementation-only change would contradict the current specification and compatibility suite.
