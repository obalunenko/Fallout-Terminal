# Master Player-Management UI Contract

## Window model

“Pop-up window” is implemented as one modal HTML `dialog` inside the existing Wails master window. No second native window, route, browser context, or desktop service is created.

The main player-configuration section retains file selection/status and exposes `#btnManagePlayers`. The previous inline detailed roster editor and inline add form are removed.

## Field behavior

- Name uses the established maximum length and is required after trimming.
- Intelligence uses a required numeric control with minimum 1, maximum 10, and step 1; frontend checks are usability feedback, not the authority boundary.
- Hacker availability uses a required select or radio group with an initially unselected state. A checkbox is not used because unchecked cannot prove that the game master made an explicit choice.
- Each row exposes a complete editable profile and submits all values atomically with its stable ID and the latest rendered coordination revision.
- Player-provided names enter the DOM through text content or input values, never HTML interpolation.

## Render states

| State | Presentation |
|---|---|
| No selected player config | Open control disabled; existing configuration guidance remains visible. |
| Inactive, empty roster | Dialog opens, shows `#playerManagementEmpty`, and enables the add form. |
| Inactive, populated roster | Detailed values plus add/update/delete controls enabled. |
| Active broadcast | Detailed values remain visible; mode banner and `aria-readonly=true` identify read-only state; every durable mutation control is disabled. |
| Mutation pending | Related controls disabled; status announced politely; duplicate submission cannot be generated by the UI. |
| Mutation rejected | Render the returned/latest authoritative state, keep the dialog open, and announce the actionable error. |
| Configuration replaced/reopened | A newer coordination revision rerenders the complete dialog; stale controls cannot submit successfully. |

`renderCoordination` remains the only roster render source. It consumes the latest `state.coordination` from bootstrap, command results, or `coordination-state` events. The dialog never patches the roster optimistically.

## Dialog lifecycle

1. `#btnManagePlayers` records itself as opener, unhides the dialog, calls `showModal()`, and focuses the close control or first enabled input.
2. Close button or Escape closes without a desktop command and restores focus to the opener.
3. Add/update awaits one desktop command. Success applies returned authoritative state; failure applies any returned state before showing the error.
4. Delete opens `#playerDeleteDialog` with a text-only player name. Cancel restores focus to that row. Confirm submits the current stable ID and latest rendered expected revision.
5. If a broadcast event arrives while either dialog is open, durable controls become unavailable immediately. Any already queued stale request is still rejected by the coordinator guard.

## Existing live assignment controls

Durable profile editing moves to the modal; broadcast-scoped assignment management does not. Logical-session rows continue to own assign, release, controller, and claimed-character transfer operations on the master screen. Their existing private methods and active-broadcast behavior remain unchanged.

## Browser acceptance matrix

- Open/close and focus restoration for populated and empty rosters.
- Exact detailed display of name, Intelligence, and Hacker availability.
- Required Hacker choice and Intelligence 1/10 acceptance plus 0/11/fraction/non-number refusal.
- Complete add/update payload including expected revision and explicit false.
- Stable row ID and order after update; confirmation/cancel behavior for delete.
- Returned-state rendering and local alert after storage or stale-revision failure.
- Reopen/reload displays persisted canonical values.
- Broadcast event while open switches to read-only without hiding details.
- A crafted stale call during broadcast returns refusal and produces no roster change.
- Existing logical-session assignment/transfer controls remain executable under their established rules.
