# Private Desktop Contract

## Master roster projection

```proto
message CharacterState {
  string character_id = 1;
  string display_name = 2;
  optional string logical_session_id = 3;
  int32 intelligence = 4;
  bool hacker_perk_available = 5;
}
```

The existing `CoordinationState.roster = 1`, `revision = 5`, bootstrap status, command result, and `coordination-state` named event remain the only master delivery paths. Values are canonical, so projection fields do not need legacy presence.

Neither attribute is added to any `fallout.terminal.player.v1` message. Public descriptors and player snapshots remain unchanged.

## Mutation request messages

```proto
message AddCharacterRequest {
  string display_name = 1;
  int32 intelligence = 2;
  optional bool hacker_perk_available = 3;
  uint64 expected_revision = 4;
}

message RenameCharacterRequest {
  string character_id = 1;
  string display_name = 2;
  int32 intelligence = 3;
  optional bool hacker_perk_available = 4;
  uint64 expected_revision = 5;
}

message DeleteCharacterRequest {
  string character_id = 1;
  uint64 expected_revision = 2;
}
```

`RenameCharacterRequest` retains its published message name and original fields 1–2 for protobuf compatibility. It becomes the explicit adapter container behind the new full-profile update path; there is no live name-only mutation after cutover. The optional Hacker field distinguishes explicit unavailable from omission. Missing Intelligence becomes zero and is rejected.

## Generated Wails service

The narrow private service exposes:

```text
AddCharacter(CharacterCreatePayload) CoordinationCommandResult
UpdateCharacter(CharacterUpdatePayload) CoordinationCommandResult
DeleteCharacter(CharacterDeletePayload) CoordinationCommandResult
```

`UpdateCharacter` replaces the exposed `RenameCharacter` method, so the allowlist gains no net method. Payload JSON uses the established lower-camel form:

```json
{
  "name": "Mara",
  "intelligence": 8,
  "hackerPerkAvailable": false,
  "expectedRevision": 42
}
```

Update additionally carries `characterId`; delete carries `characterId` and `expectedRevision`. Go payloads preserve Hacker presence long enough to reject omission. Root adapters route every payload through the protobuf message before canonical validation.

## Validation and authorization order

1. Validate required stable ID where applicable, trimmed name, Intelligence range, Hacker presence, and expected revision representation at the root private boundary.
2. Enter the coordinator commit lock.
3. Require expected revision to equal the current canonical revision.
4. Require an active player configuration and no active broadcast.
5. Require the target ID to exist for update/delete.
6. Build and validate one complete candidate roster.
7. Perform the conditional complete-file save.
8. Install the candidate and new content digest, commit one revision, and publish one detached effect.

Rejections return `ok=false`, a safe actionable error, and the latest authoritative `state`. They do not allocate an ID, save, increment revision, or publish an event.

## Ordering and idempotence

- All three mutation types share the coordinator's total order.
- The first successful command changes `CoordinationState.revision` exactly once.
- A retry with the same expected revision is stale and cannot repeat the write.
- A no-op update may return the unchanged authoritative state without a write or revision.
- A broadcast-start transition ordered before the mutation causes rejection; a mutation ordered before broadcast start may complete, after which the start event carries the newer roster.

## Capability verification

- The generated Wails inventory contains `AddCharacter`, `UpdateCharacter`, and `DeleteCharacter`, and no `RenameCharacter` or generic dispatcher.
- Public player descriptors contain no Intelligence, Hacker, player-config path, digest, or roster mutation request.
- Private projection adapters round-trip field numbers, Hacker false, expected revision, identity, and order without mutable aliases.
- Generated protobuf and Wails files are regenerated by pinned repository tools and never edited manually.
