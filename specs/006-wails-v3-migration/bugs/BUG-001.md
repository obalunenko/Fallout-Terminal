# Bug Report: Development launch shows a generic executable icon

**Type**: Implementation drift
**Severity**: Medium
**Feature**: Wails v3 Runtime Migration (`006-wails-v3-migration`)
**Reported**: 2026-08-14
**Status**: Patched
**Patched**: 2026-08-14

## Description

Running `make dev` starts the native application without the project-owned Fallout Terminal icon. macOS displays the generic executable icon instead.

The `make dev` target delegates to the canonical `go run ./cmd/build dev` workflow, so the symptom is not specific to Make. The development build graph compiles `build/bin/Fallout Terminal` and launches that bare Mach-O executable directly. It does not assemble a development `.app`, install `build/darwin/Info.dev.plist`, or generate/install `build/appicon.png` as `icon.icns`. The packaging graph does perform those metadata and icon steps, which is why the packaged application has the expected icon.

## Root Cause Analysis

`Makefile` maps `make dev` to `go run ./cmd/build dev`. In `internal/buildtool/buildtool.go`, the `dev` and `run` actions append `buildSteps()`, which compiles `build/bin/Fallout Terminal`, and then execute that file directly. Those steps never create an `.app` bundle or install application metadata/resources.

The icon-generation step exists only in `packageSteps()`, where `build/appicon.png` becomes `Contents/Resources/icon.icns` and `build/darwin/Info.plist` declares it through `CFBundleIconFile`/`CFBundleIconName`. Although `build/darwin/Info.dev.plist` declares the same icon, no active source references that file. macOS therefore sees the development process as a standalone executable and uses the generic executable icon.

The bug survived because build-plan tests assert ordering and package sign/resource behavior, while native development acceptance records the window, process, listener, persistence, and cleanup behavior but not application identity or icon presentation.
