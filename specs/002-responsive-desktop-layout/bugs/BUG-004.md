# Bug Report: Hack Rows Do Not Fill Available Column Width

**Type**: Spec gap
**Severity**: Medium
**Feature**: 002-responsive-desktop-layout (Responsive Desktop Player Layout)
**Reported**: 2026-08-10
**Status**: Patched
**Patched**: 2026-08-10

## Description

Each memory-dump row in the on-screen hacking game renders its address and 12-character board data at the general hacking font size, even when the row has substantially more usable horizontal space inside its hacking column. The row data consequently appears undersized and leaves avoidable empty space instead of filling the useful width of both hacking columns.

The hacking-row font must adapt to the actual rendered column capacity so the address and cell data use the maximum useful row width while the same readable font size is retained across equivalent rows. Width fitting must remain constrained by the existing single-screen contract: all 16 rows in each column, the attempts display, activity log, and input preview must stay visible without clipping, overlap, scrolling, or pagination, including with fallback fonts and at the supported viewport and zoom matrix.

## Artifact Traceability

### spec.md

- **Affected user story**: **User Story 2 — Use the terminal across desktop screen sizes**. Acceptance Scenarios 2 and 5 require the hacking board to remain visible and usable, keep hacking text at least as large as primary terminal text, and adapt its geometry to fit one screen. They do not require the rendered address-and-cell data in each row to expand to the useful width of its column.
- **Affected requirements**:
  - **FR-005** requires all hacking regions and interactions to remain visible and usable, but does not define efficient horizontal use within each board column.
  - **FR-006** requires every font role to derive from the shared responsive scale and preserve the role hierarchy. It does not say how a hacking-row fit may enlarge text from that baseline when the board has spare width.
  - **FR-015** requires hacking text to meet the primary-text size floor and says the board must use the available content region without appearing disproportionately reduced, but it provides no measurable row-width occupancy or maximum-use criterion.
  - **FR-016** permits board geometry, gaps, padding, log allocation, and orientation to adapt for a single-screen fit, but does not explicitly include a column-aware hacking-row font size or define how width growth is balanced against the fixed 16-row height.
- **Affected success criteria**:
  - **SC-007** verifies that font roles preserve their defined ratios, but does not verify that hacking rows use their available width.
  - **SC-009** verifies the hacking text floor, complete visibility, containment, and absence of scrolling or pagination, but has no assertion for excessive unused width between the last board glyph and the column boundary.
- **Gap identified**: The specification defines a minimum hacking text size and complete-screen containment, not a maximum useful size for the fixed address-plus-12-character row. It therefore permits a layout whose column containers fill the board while the actual row glyphs occupy only part of each container. The specification must also clarify how column-aware enlargement coexists with FR-006's shared responsive font scale.

## Root Cause Analysis

The earlier responsive fixes concentrated on preventing undersized text, overflow, and clipped descendants. The production stylesheet gives `.hack-col` and `.hack-cells` flexible width, but `.hack-board` inherits `--font-hack` from the general `--terminal-scale`, which is capped independently of each rendered column's capacity. The runtime fit logic only applies compact, stacked, and tight classes when content overflows; it has no inverse path that increases the common row font when columns contain spare space.

Because the specification and regression suite establish only a font-size floor and containment checks, the column containers can satisfy their geometry tests while the address-and-cell glyphs remain noticeably narrower. This is primarily a specification and acceptance-test omission, with a corresponding implementation behavior that the current artifacts allow.
