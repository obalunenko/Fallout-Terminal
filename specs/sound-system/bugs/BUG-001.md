## Description

Ambient playback and browser audio activation are controlled by page-global gesture state rather than an explicit live-terminal lifecycle.

Once the ambient asset is ready, the first document click calls `tryStartAmbient()` and can start the loop while the player is still idle, waiting for assignment, or otherwise has no accepted live terminal. `TERMINAL_LIVE` also attempts to start ambience and clear paths pause it, but those client calls do not prevent the earlier idle-page start because `client/sound.js` does not know whether ambience is currently permitted.

The same activation boundary is one-shot and pointer-only. The first click permanently sets `userGestured`, and `enableWebAudio()` caches `webAudioReady` even when the context fails to become `running`. Later clicks cannot retry activation, while keyboard-only interaction never attempts activation at all. These limitations can leave both ambient and one-shot sounds silent for the remainder of the page lifetime after a recoverable first failure.

The visual terminal remains usable, so the defect is not data-destructive and does not compromise canonical state. It can nevertheless produce unwanted audio outside a live broadcast and inconsistent audio availability for keyboard-only or initially ineligible clients.

## Reproduction

### Idle ambient start

1. Open the player page with a valid ambient asset available.
2. Wait for `/api/sounds/ambient` and the asset to load.
3. Before a live terminal is published, click anywhere in the document, including an idle, waiting, or selection view.
4. Observe that the ambient element is allowed to call `play()` even though no live terminal exists.

### Non-recovering activation

1. Open the player page in a state where the first AudioContext resume attempt remains suspended or otherwise resolves ineligible.
2. Click once; `webAudioReady` resolves false and `userGestured` becomes true.
3. Make a later eligible pointer or keyboard interaction after playback could be allowed.
4. Observe that `enableWebAudio()` is not retried and one-shot audio remains unavailable until reload.

## Expected Behavior

- ~~Ambient playback is permitted only while an accepted live terminal is active and browser user-activation requirements have been satisfied.~~ **Adjusted by BUG-001**: Ambient playback is permitted only while an accepted live terminal is active; the client attempts immediately and either starts when autoplay is permitted or retains the request for a qualifying-gesture retry when blocked.
- Idle, connecting, character-selection, assigned-waiting, and cleared states remain ambient-silent.
- Accepted live publication immediately attempts to start or resume ambience; every clear/reset path pauses it and revokes the live ambient request.
- A failed or suspended initial Web Audio activation can retry on a later qualifying user gesture without creating duplicate contexts or concurrent initialization work.
- Pointer and keyboard activation are attempted when the browser recognizes them as user activation; browser rejection remains silent and non-blocking.

## Pre-fix Actual Behavior

- `client/sound.js` tracks `ambientReady` and `userGestured`, but not whether a live terminal currently permits ambience.
- The first document `click` directly invokes `tryStartAmbient()` regardless of player phase or live state.
- `userGestured` prevents later gesture handling after the first click.
- `webAudioReady` retains a promise that resolved false, so later calls return the same failed result rather than retrying.
- No ambient lifecycle test currently proves idle silence, live-only start, clear/reset stop, reconnect behavior, or activation recovery.

## Pre-fix Implementation Trace

- `client/sound.js` `setupAmbient()` creates the ambient element and immediately calls `tryStartAmbient()` after readiness.
- `client/sound.js` `tryStartAmbient()` checks only `ambientReady`, `userGestured`, element existence, and `paused`; it has no live-state condition.
- The document `click` listener sets `userGestured`, calls `enableWebAudio()`, and calls `tryStartAmbient()` only inside the first-gesture branch.
- `enableWebAudio()` returns the existing `webAudioReady` promise before evaluating a new activation attempt, including when that promise previously resolved false.
- `client/client.js` calls `tryStartAmbient()` for accepted `TERMINAL_LIVE` and `stopAmbient()` for terminal/mirror clear, but it cannot revoke or express eligibility inside the sound module.
- Existing Playwright audio doubles observe Web Audio source starts; they do not provide an observable ambient `Audio` lifecycle.

## Root Cause Analysis

The initial design treated “the browser received a gesture” as both autoplay eligibility and ambient lifecycle permission. That was sufficient to unlock a simple global hum, but it did not model the independent condition that a live terminal must be active. Live-start and clear-stop calls were later layered into `client/client.js` without moving lifecycle ownership behind a single guarded state transition, leaving the original page-global click path able to bypass live state.

The same first-gesture shortcut made activation state terminal: `userGestured` is a one-way boolean and `webAudioReady` is a one-way promise cache. The design correctly coalesces concurrent initialization, but it does not distinguish an in-flight attempt, a successful eligible context, and a failed attempt that should be retried later.

Verification concentrated on exact-once hacking outcome audio and graceful failure. Because the test harness observes Web Audio buffer sources rather than `HTMLAudioElement`, it could not detect idle ambient start or incomplete ambient stop/retry behavior.
