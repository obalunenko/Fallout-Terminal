# Bug Report: Real ngrok Player Never Receives the Initial Subscribe Snapshot

**Type**: Dependency issue
**Severity**: Critical
**Feature**: `007-embedded-ngrok-access`
**Reported**: 2026-08-16
**Status**: Patched
**Patched**: 2026-08-16

## Description

With an active game session, a player can open the public ngrok URL and reach the player page, but
the page remains indefinitely on `УСТАНОВКА СВЯЗИ...`. If public access is stopped and the same
session is opened through localhost, the player receives the current state and works normally.

The symptom proves that public static delivery is available while the initial generated ConnectRPC
`PlayerService/Subscribe` snapshot does not complete through the real ngrok path. Local success
isolates the observed failure from the authoritative player session and basic local player server
availability. No credential value, Authorization header, cookie, or raw provider diagnostic was
captured for this report.

## Root Cause Analysis

The primary cause is an external-dependency assumption that was never validated on a real endpoint
before completion. The research explicitly recorded that an ngrok edge authentication action might
buffer or otherwise interfere with a non-empty long-lived ConnectRPC server stream. BUG-001 accepted
Traffic Policy Basic Auth for personal sharing while deferring the decisive real streaming test.

The deterministic protected browser fixture emulates an edge and successfully streams, but cannot
prove ngrok Traffic Policy behavior. The opt-in Go integration test verifies missing/wrong/correct
Basic Auth only with a finite HTTP GET returning `204`; it does not execute `Subscribe`. The real
Playwright public endpoint journey does cover `Subscribe`, but quickstart records it and the other
real provider journeys as `NOT RUN` because credentials were not supplied during qualification.

The user's first available real exercise therefore exposed the untested provider boundary. The
proximate transport failure is not yet proven: `/Subscribe` may be rejected during credential
replay, accepted but buffered before the first frame, transformed incompatibly, or affected by an
account/edge capability. A patch must collect only secret-free status/content-type/timing/upstream
evidence before selecting the implementation change.

## Recommended Fix

1. Run `$speckit-bugfix-patch BUG-003` to update the affected spec, plan, contract, and tasks with a
   blocking real-stream disposition and dependency-ordered RED/GREEN verification work.
2. First capture a secret-safe reproduction: `/Subscribe` response status and content type,

   Authorization, cookies, token, password, or raw provider diagnostics.
3. If real evidence shows Traffic Policy does not preserve the stream, replace that authentication
   boundary with the plan's non-buffering application-owned ingress fallback. Keep one authoritative
   player service on port 3690, require Basic Auth for static/unary/streaming public requests, and
   leave direct local/LAN access without a challenge.
4. Run `$speckit-bugfix-verify BUG-003` to confirm artifact consistency.
5. Resume `$speckit-companion-implement` to implement the corrective tasks test-first and require a
   real authenticated initial snapshot plus a later update before closing BUG-003.

## Patched Decision

1. The observed real static-success/`Subscribe`-stall result makes ngrok Traffic Policy Basic Auth
   non-normative for the active production path; deterministic fixtures cannot override it.
2. The ngrok SDK keeps account authentication and endpoint transport only. It receives no player
   username/password and forwards to one owned loopback-only application ingress.
3. The ingress starts deny-all, then atomically activates exact validated public Host plus scoped
   Basic Auth before URL publication. It strips Authorization and streams without buffering to the
   sole authoritative player service on port 3690.
4. Stop/failure/reconfigure/shutdown deny ingress admission before URL withdrawal and endpoint/
   ingress close. Direct local/LAN clients continue to bypass the ingress without challenge.
5. T087–T095 own RED diagnostics, implementation, deterministic qualification, and mandatory real
   closure. No historical task is reopened; T095 and BUG-003 remain incomplete at implementation
   level until a real packaged endpoint delivers the initial snapshot and a later update.
6. The verification follow-up supersedes residual BUG-001 direct-upstream, Host, shutdown-order,
   lifecycle-cardinality, and MVP guidance without adding or reopening tasks.
7. For repeat tests, the canonical dev/test composition may read only the four FR-056 environment
   names before persisted/Keychain fallback. Domain and username may prefill; token/password remain
   presence-only and scoped. ~~No value is persisted~~ **BUG-003 reconciliation** no value is
   implicitly persisted, no environment-derived secret enters Save/Keychain, and explicit Save may
   retain only visible non-secret values. No secret value is logged or honored by packaged
   production, and loading never auto-starts. T093 adds RED coverage, T094 implements the adapter,
   and T095 reruns qualification.
8. The second verification reconciliation also removes residual direct-upstream/Traffic Policy,
   Keychain-only dev-source, and withdraw-before-deny wording. It adds no task and changes no task
   completion state.
9. The non-secret username reconciliation permits username/domain only on existing approved
   settings/master snapshot/UI surfaces, while token/password remain presence-only and password
   confinement remains unchanged. It adds no task and changes no task completion state.
