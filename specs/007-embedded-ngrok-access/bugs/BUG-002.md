# Bug Report: Successful Embedded ngrok Start Immediately Stops the Endpoint

**Type**: Implementation drift
**Severity**: Critical
**Feature**: `007-embedded-ngrok-access`
**Reported**: 2026-08-16
**Status**: Patched
**Patched**: 2026-08-16

## Description

Starting public access with an otherwise valid embedded ngrok configuration can briefly acquire an
endpoint and then immediately transition to the generic provider-stopped failure while local/LAN
play remains usable.

`PublicAccessManager` correctly bounds the startup operation with a cancellable context and cancels
that context after `TunnelService.Start` returns. The embedded SDK adapter incorrectly passed the
same startup context to `Agent.Forward`. In ngrok SDK v2.1.4 that context also owns the continuing
forwarder lifetime, so the manager's normal successful-start cleanup stopped the acquired endpoint.
The endpoint monitor then observed `Done` and published the redacted provider-stopped status.

Expected behavior: the startup context may cancel an acquisition that has not completed, but after
a protected endpoint is acquired and committed its lifetime remains owned by the endpoint until an
explicit stop, reconfigure, failure cleanup, or application shutdown.

Observed behavior: completion of the successful startup operation canceled the active forwarder.
No account token, player password, or raw provider diagnostic is required or recorded to reproduce
the defect.

## Reproduction

1. Configure public access through the packaged application's UI with user-owned ngrok credentials.
2. Start public access.
3. Observe the endpoint become available to the adapter, followed immediately by
   `The public-access provider stopped unexpectedly.` in the UI.
4. Confirm that local/LAN mode continues to work.

A deterministic fake reproduces the lifecycle error by closing its `Done` channel when the context
passed to `Forward` is canceled. Before the corrective implementation,
`TestEmbeddedNgrokEndpointLifetimeSurvivesCompletedStartupContext` fails with
`completed startup context stopped the owned endpoint`.

## Artifact Traceability

- **spec.md**: User Story 2 acceptance scenarios 1 and 4, FR-016, FR-020, FR-022, FR-029,
  FR-032, FR-034, and SC-001 require a successfully acquired protected endpoint to reach and remain
  ready until a later lifecycle intent. The artifacts did not explicitly distinguish the bounded
  startup-operation context from the lifetime of the committed endpoint.
- **plan.md**: section 4 requires a generation-aware manager, private acquisition before
  publication, explicit endpoint ownership, `Done` monitoring, cancellation, and cleanup. The SDK
  adapter design did not specify the startup-to-owned-lifetime context handoff.
- **contracts/tunnel-service.md**: the lifecycle contract required cancellation and explicit Close
  but did not distinguish the acquisition context from the committed endpoint's owned lifetime or
  define a strictly redacted post-`Done` failure extension.
- **tasks.md**: T037, T038, T041, T055, T057, T061, T063, and T065 covered adapter/manager startup,
  cancellation, `Done`, and cleanup, but their deterministic fakes did not model ngrok's use of the
  `Forward` context as the continuing forwarder lifetime. Corrective test-first and implementation
  work must be added without rewriting the completed historical tasks.
- **Implementation**: `internal/tunnel/ngrok.go` passed the manager startup context directly to
  `Agent.Forward`; `internal/tunnel/manager.go` then canceled that context after Start completed as
  designed.

## Required Correction

1. Add a deterministic RED regression proving that cancellation of a completed startup operation
   does not stop the committed endpoint, while cancellation before commit still aborts acquisition.
2. Give the SDK forwarder an endpoint-owned context with an explicit pre-commit abort / post-commit
   ownership handoff; cancel it from endpoint `Close`.
3. Preserve safe actionable disconnect evidence by retaining only a validated `ERR_NGROK_<digits>`
   code and a fixed application message; discard raw SDK diagnostics and all secret-bearing text.
4. Run focused tunnel unit, race, and vet gates, then the canonical build and secret-leak scan.
5. Keep the real-provider retry credential-gated; without explicit opt-in credentials record it as
   `NOT RUN` rather than treating deterministic tests as real endpoint proof.

## Patch Closure

- T084 reproduced the defect before production changes and now protects the exact SDK context
  lifetime contract.
- T085 implemented the pre-commit abort / post-commit ownership handoff and safe disconnect-code
  propagation and synchronized the provider-neutral lifecycle contract.
- T086 passed focused tunnel unit and race tests, tunnel vet, the canonical build, and the
  secret-leak scan. The real credentialed provider retry is `NOT RUN` pending the user's explicit
  opt-in test after relaunching the rebuilt application.
