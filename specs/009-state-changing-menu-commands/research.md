# Исследование: команды, изменяющие состояние пунктов меню

## Решение 1: разделить авторскую настройку и серверное состояние выполнения

**Decision**: Исходное название и текст успеха продолжают использовать существующие поля команды `name` и `text`. Необязательная настройка `stateChange` добавляет название после выполнения и приватный текст запроса мастеру. Выполненные снимки хранятся отдельно в `Terminal.commandStates`, индексированном стабильным ID команды; сам терминал задаёт вторую часть идентичности.

**Rationale**: Авторская настройка редактируется мастером, а выполненное состояние принадлежит игровому миру и изменяется только доверенным серверным переходом. Раздельное хранение позволяет при любом полном автосохранении редактора сохранить канонические выполненные снимки, удалить их вместе с удалёнными командами и не связывать состояние с названием либо позицией узла. Отсутствие обоих новых необязательных полей естественно означает обычную или ещё не выполненную команду в существующем JSON version 1.

**Alternatives considered**: Хранить снимок прямо в узле команды проще для проекции дерева, но смешивает редактируемое и серверное состояние и повышает риск его перезаписи устаревшей копией документа. Хранить только булев признак недостаточно: после выполнения название и результат должны быть заморожены независимо от дальнейшего редактирования. Повышение версии JSON не требуется и противоречит принятому решению о совместимости version 1.

## Решение 2: все долговечные мутации проходят через один упорядоченный сервис сессии

**Decision**: `internal/session.Service` становится единственным владельцем монотонной ревизии открытого документа и предоставляет ID-адресованные атомарные операции выполнения, сброса одной команды и сброса терминала. Обычное полнодокументное сохранение объединяет входящий авторский документ с каноническими состояниями сохранившихся `(terminalID, commandID)` и удаляет состояния отсутствующих команд.

**Rationale**: Текущий worker уже сериализует записи и использует атомарную замену файла, но новый серверный переход может состязаться с очередным автосохранением полной JS-копии. Общая очередь, единая ревизия и merge-правило не позволяют старому документу стереть прогресс игрока. Удаление команды остаётся единственным обычным авторским изменением, которое очищает связанное состояние без отдельного сброса.

**Alternatives considered**: Прямой вызов `Storage.WriteAtomic` из координатора обошёл бы epoch/revision-порядок и мог быть перезаписан уже принятой записью. Независимый счётчик ревизий в `App` и отдельный счётчик для игровых мутаций создают коллизии и не дают фронтенду надёжно определить более новый документ.

## Решение 3: разделить runtime-запрос и долговечное выполнение

**Decision**: Первый `Navigate` после проверки полномочий создаёт только канонический runtime-запрос ожидания и публикует его игрокам и мастеру. Отдельное приватное решение мастера разрешает этот запрос. Только для approve `internal/control.Service` вызывает узкий синхронный `CommandStateStore`, аналогичный `RosterStore`, и устанавливает выполненную runtime-проекцию лишь после долговечного успеха.

**Rationale**: Запрос обязан быть видимым до решения мастера, но не является частью мира и не требует записи. Сериализованный координатор создаёт ровно один pending-запрос, блокирует остальные shared actions и сохраняет его при отключении инициатора. Approve использует persist-before-success: ошибка записи очищает ожидание без completed name/result и сообщает ошибку мастеру и контроллеру. Долговечная запись, а не ограниченный replay-cache, остаётся exactly-once барьером после перезапуска.

**Alternatives considered**: Сохранять pending-запрос в session JSON противоречит решению отменять его при завершении контекста. Публикация успеха с последующим асинхронным сохранением допускает результат, который исчезнет после ошибки или перезапуска.

## Решение 4: оставить выбор игрока в существующем Navigate, а решение сделать приватным

**Decision**: Player client отправляет неизменённый по смыслу `NavigateCommand{node_id}`. Для ещё не выполненной stateful-команды сервер создаёт `PendingCommandExecution` с собственным стабильным request ID. Master frontend получает pending через расширенный приватный `CoordinationState`, показывает диалог с авторским текстом и вызывает новый allowlisted метод `ResolveCommandExecution` с `approve` или `reject` и request ID.

**Rationale**: Выбор команды уже является сервер-авторитетной unary-мутацией с проверкой controller/broadcast/terminal и request replay. Решение принадлежит только доверенному desktop boundary, поэтому его нельзя кодировать как player-поле или публичный RPC. `CoordinationState` уже имеет bootstrap snapshot и event-публикацию, так что мастер восстанавливает диалог после перезагрузки frontend без потери текущего runtime-запроса.

**Alternatives considered**: `confirmed` от player client не удовлетворяет требованию одобрения мастером. Новый публичный approve RPC нарушает разделение private/public capabilities. Отдельное transient Wails event без pending в bootstrap-состоянии может потеряться до подписки frontend.

## Решение 5: публиковать только эффективное состояние команды

**Decision**: Публичное дерево строится из авторской конфигурации и долговечного снимка, но текст запроса мастеру в player projection не передаётся. Отдельная публичная `CommandExecutionPresentation` описывает `pending` или `rejected`: pending показывает всем фиксированный текст «Выполняется запрос» и блокирует shared actions, rejected показывает «Запрос отклонён» до возврата контроллера. После approve полная проекция содержит замороженные выполненное название и результат.

**Rationale**: Полная `TerminalPresentation` уже доставляется контроллеру, наблюдателям и переподключившимся клиентам с серверной ревизией. Явная runtime-презентация позволяет snapshot/reconnect увидеть то же ожидание или отказ, не подменяет authored command text и не раскрывает приватный prompt. Approve, reject и возврат из rejection получают отдельные монотонные live revisions.

**Alternatives considered**: Подменять `ContentCommand.text` служебными сообщениями смешивает authored/durable и runtime-значения. Локальный spinner только у инициатора расходится с observers и reconnect. Передавать player client текст мастерского запроса раскрывает ненужную приватную конфигурацию.

## Решение 6: использовать CoordinationState для запроса и отдельное событие для документа

**Decision**: Временный `PendingCommandExecution` входит в существующий приватный `CoordinationState` и `coordination-state` event. После любой долговечной ID-адресованной мутации backend дополнительно отправляет мастеру `session-state` с каноническим документом и document revision. Master frontend дедуплицирует диалог по pending request ID и принимает session document только с более новой ревизией.

**Rationale**: Coordination snapshot закрывает потерю события при поздней подписке или reload frontend. Игровое выполнение обходит текущий `App.SaveSession`, поэтому отдельная durable-проекция не даёт мастеру редактировать устаревшую копию и показывать неверный save status. Оба payload остаются за Wails-границей; session-side merge защищает уже поставленные в очередь сохранения.

**Alternatives considered**: Fire-and-forget dialog event теряется до подписки. Периодическое перечитывание создаёт окно рассинхронизации. Публичное событие с prompt или полным документом нарушает private/player separation.

## Решение 7: сбросы являются доверенными атомарными командами

**Decision**: Master frontend подтверждает отдельный сброс команды и сброс всех состояний терминала, после чего вызывает два явно типизированных метода приватного desktop service. Backend повторно валидирует стабильные ID, сохраняет изменение через общий session pipeline и, если терминал активен, в той же принятой координационной транзакции публикует обновлённую проекцию игрокам.

**Rationale**: Сброс — единственный обратный переход игрового мира. Явные команды не позволяют обычному редактированию JSON случайно имитировать сброс и обеспечивают одинаковые гарантии сохранения и публикации для активного и неактивного терминала.

**Alternatives considered**: Удаление состояния непосредственно из JS-документа не может доказать атомарность и конфликтует с серверным владением. Универсальный метод мутации расширил бы доверенную поверхность и ослабил проверку назначения операции.

## Решение 8: использовать существующие инструменты и совместимые добавления схем

**Decision**: Новые зависимости не вводятся. Изменяются только исходные protobuf-схемы с новыми номерами полей/enum, после чего generated Go/ECMAScript и Wails bindings обновляются штатными генераторами; JSON остаётся version 1 с сохранением неизвестных полей.

**Rationale**: В проекте уже есть атомарное хранилище, ConnectRPC, потоковые ревизии, Wails events, Buf compatibility и браузерные тесты. Совместимые добавления достаточны для всей функции и сохраняют воспроизводимость.

**Alternatives considered**: Новый storage engine, event bus или клиентское хранилище не устраняют существующую гонку полнодокументных сохранений и увеличивают поверхность сопровождения.

## Решение 9: pending-запрос принадлежит broadcast/terminal, а не соединению игрока

**Decision**: Pending-запрос хранит broadcast ID, terminal ID, command ID и server-generated request ID, но после принятого выбора не зависит от жизни инициировавшего соединения. Отключение контроллера сохраняет запрос; end broadcast, terminal switch и shutdown отменяют его без записи. Закрытие диалога отправляет reject.

**Rationale**: Полномочия контроллера проверяются в момент выбора. Случайный reconnect после принятия не должен отменять решение, уже переданное мастеру. Одновременно запрос нельзя переносить в другой terminal/broadcast context или восстанавливать после restart, поскольку спецификация определяет его как временный.

**Alternatives considered**: Привязка к stream/recognition handle делает результат зависимым от сети. Долговечное восстановление pending создаёт устаревшее одобрение в новом контексте. Блокировка terminal lifecycle до решения мастера противоречит явно выбранной автоматической отмене.
