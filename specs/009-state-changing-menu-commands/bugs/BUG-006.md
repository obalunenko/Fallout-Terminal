# Bug Report: Тестовый input не закрепляет полный набор узлов и имя запрошенной команды

**Type**: Untested flow
**Severity**: Medium
**Feature**: `009-state-changing-menu-commands`
**Reported**: 2026-08-18
**Status**: Patched
**Patched**: 2026-08-18

## Description

Вводная session/fixture для проверки state-changing команд должна быть самодостаточной: содержать как минимум по одному явному узлу каждого пользовательского вида — папку, запись и команду. Каждая команда именно в этом тестовом input должна начинать в исходном состоянии и иметь валидную `stateChange`-настройку, поэтому её выбор всегда создаёт ожидание решения мастера, а не выполняется как ordinary-команда и не открывает заранее сохранённый completed result.

В master-уведомлении должны одновременно и явно отображаться:

1. точное отображаемое имя команды, запросившей выполнение;
2. настроенный `confirmationText` этой команды;
3. действия одобрения и отклонения.

Требование «любая команда ожидает подтверждения» относится только к назначенному тестовому input и не отменяет поддержку ordinary-команд в произвольных пользовательских или legacy-сессиях.

Сейчас fixture-формы расходятся и не защищены единым тестовым контрактом:

- `stateChangingApprovalTarget()` в `tests/browser/fixture-server/main.go` содержит entry и state-changing command, но не явную дочернюю папку помимо корня;
- approval-session в `tests/browser/fixtures/desktop-bindings.js` дублирует дерево отдельно и содержит только команду под корнем, без записи и явной папки;
- authoring fixture в Go и JavaScript не содержит записи, а команда `emergency-lights` остаётся ordinary без `stateChange`;
- `sessions/demo.json` содержит нужные типы и initial state-changing команды, но существующая проверка утверждает только отсутствие `commandStates` и не закрепляет состав узлов или `stateChange` у каждой команды;
- master UI уже имеет путь `pending.commandName → «КОМАНДА: …»`, однако browser journey проверяет только `confirmationText`, поэтому отдельное отображение имени запрошенной команды может исчезнуть незамеченным.

## Root Cause Analysis

Артефакты отдельно зафиксировали совместимость ordinary-команд, initial demo-сессию, authoring flow и approval lifecycle, но не определили общий контракт входных данных для теста. Поэтому похожие session trees были продублированы в Go, JavaScript и JSON и постепенно разошлись по составу узлов и состояниям команд.

Master contract уже переносит `command_name`, и UI уже способен вывести `КОМАНДА: <имя>`, но тест использует confirmation text, который сам содержит имя команды. Такая проверка не доказывает, что мастер получает отдельную однозначную идентификацию команды, и пропустит регрессию command-name projection или rendering.
