# Bug Report: Общий сброс мастера не возвращает команду в исходное состояние

**Type**: Implementation drift
**Severity**: High
**Feature**: `009-state-changing-menu-commands`
**Reported**: 2026-08-17
**Status**: Patched
**Patched**: 2026-08-17

## Description

После того как мастер подтверждает действие «Сбросить все состояния», команда, которая до сброса находилась в состоянии `COMPLETED`, остаётся выполненной. Нажатие и подтверждение общего сброса не приводят к наблюдаемому переходу команды в исходное состояние.

**Expected**: подтверждённый общий сброс одним атомарно сохранённым изменением удаляет выполненные состояния всех и только команд выбранного терминала. В мастерском интерфейсе и во всех активных player-представлениях команды сразу отображаются в исходном состоянии и остаются такими после повторного открытия той же writable-сессии.

**Actual**: по завершении действия хотя бы одна команда выбранного терминала продолжает отображаться как выполненная.

Это повторная регрессия сценария общего сброса, ранее затронутого BUG-001. В отличие от первоначальной проблемы bundled demo, новое наблюдение было сформулировано для действия мастера как нарушение конечного состояния; production-разрыв локализован и устранён, как описано ниже.

## Root Cause Analysis

Session service корректно удалял `commandStates`, атомарно сохранял новую document revision и возвращал каноническую сессию. Разрыв находился в обновлении активного runtime.

Во время `RefreshActiveTerminal` карта выполненных состояний заменялась канонической, но текущий `Nav.CommandNodeID` сохранялся. Если игрок находился на экране результата только что сброшенной completed-команды, навигация продолжала указывать на этот результат даже после удаления соответствующего snapshot. Поэтому документ уже находился в исходном состоянии, а активная player-проекция продолжала показывать команду как выполненную.

Дополнительно browser fixture ранее очищал `commandStates` непосредственно в JavaScript и самостоятельно публиковал `session-state`. Это подтверждало frontend-сценарий, но не проверяло реальный App/session/coordinator path и скрывало дефект runtime refresh.

## Resolution

1. `RefreshActiveTerminal` теперь очищает `Nav.CommandNodeID`, только если текущая команда была completed до обновления и её snapshot отсутствует в новом каноническом `commandStates`.
2. Навигация обычных команд и completed-команд, состояния которых сохранились, не изменяется.
3. Master frontend принимает успешный reset только при более новой document revision и канонической сессии без сброшенных состояний.
4. Browser binding проксирует reset в Go fixture/backend и больше не изменяет `commandStates` самостоятельно.
5. Добавлены production-faithful проверки нескольких completed-команд, точного terminal scope, одной durable revision, controller/observer convergence и повторного открытия того же JSON.
