# Bug Report: Protobuf Generation Bypasses Buf

**Type**: Spec conflict
**Severity**: High
**Feature**: 005-connectrpc-protobuf-migration
**Reported**: 2026-08-13
**Status**: Patched
**Patched**: 2026-08-13

## Description

Protobuf generation must run only through the pinned Buf CLI and the existing
Buf v2 generation templates. The current generation path instead downloads and
verifies Google `protoc` v35.0, invokes it directly with local plugins, requires
generated Go headers to report `protoc v7.35.0`, and repeats the standalone
compiler check in CI.

This is incorrect for Buf generation. The Buf CLI compiles protobuf sources in
process with its own Go compiler instead of invoking Google's reference
`protoc`; pinning the Buf CLI therefore pins the compiler implementation used by
`buf generate`. A Buf-generated Go header may report `protoc unknown`, and that
provenance is acceptable. Verification should pin and check Buf plus the code
generation plugins and runtimes, not require a standalone `protoc` version.

The current drift is visible in:

- `scripts/proto-generate.sh`, which calls `scripts/ensure-protoc.sh` and invokes
  the downloaded compiler directly instead of running `buf generate` with
  `proto/buf.gen.go.yaml` and `proto/buf.gen.es.yaml`.
- `scripts/proto-check.sh`, which rejects valid Buf-generated Go output unless
  every `.pb.go` header contains `protoc v7.35.0`.
- `.github/workflows/wails-macos.yml`, which installs and verifies standalone
  `protoc` before schema checks.
- `proto/toolchain.env` and `scripts/ensure-protoc.sh`, which add an unnecessary
  second compiler distribution, platform checksum matrix, and generation-time
  download path.

Official basis: [Buf's New Compiler](https://buf.build/blog/bufs-new-compiler)
states that the Buf CLI uses a custom in-process protobuf compiler and does not
shell out to `protoc`.

## Root Cause Analysis

FR-133's phrase “protobuf compiler” was interpreted as a requirement to install
and pin Google's standalone `protoc`. During convergence, `protoc unknown` in
Buf-generated headers was consequently treated as missing provenance, and T129
introduced a parallel direct-compiler path to force a versioned header.

That interpretation did not account for Buf's in-process compiler and
contradicted the plan's explicit two-pass `buf generate` verification path. The
result duplicates compiler ownership, bypasses the checked-in Buf templates,
adds a clean-environment network dependency, and causes verification to reject
valid artifacts generated by the project's intended pinned toolchain.
