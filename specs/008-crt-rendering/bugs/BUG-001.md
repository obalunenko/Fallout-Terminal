# Bug Report: Hack Puzzle Codes Render Without Reveal Animation

**Type**: Spec gap
**Severity**: Medium
**Feature**: CRT Rendering and Motion Effects (`008-crt-rendering`)
**Reported**: 2026-08-16
**Status**: Patched
**Patched**: 2026-08-16

## Description

When the player enters the hacking puzzle, the complete code grid is rendered at once. The hack puzzle has no progressive rendering animation, so its initial presentation does not provide the purposeful terminal reveal expected for the codes on that screen.

Expected behavior: on the first presentation of a new hacking puzzle, its code rows or cells reveal progressively in source order. The precise reveal unit and timing must be defined by the patched specification. The reveal must remain presentation-only and must not change authoritative hacking state or allow interaction with code that is not yet visible.

Actual behavior: `renderHackColumns()` builds all hacking-column markup and assigns it to `hackColumns.innerHTML` in one operation. The existing reveal controller is used only for folder, record, and command content, so the complete hacking board becomes visible atomically.

## Root Cause Analysis

The feature artifacts translated “progressive content reveal” into a closed list of folder, record, and command surfaces. Hacking was included in shell, color, viewport, and fit verification, but its code grid was explicitly modeled as non-revealable. Consequently, the implementation correctly routes list/text content through `revealInto()` while retaining the existing atomic `innerHTML` render for hack columns, and the test suite checks hacking containment, hover styling, fitting, and operability without asserting initial code-render animation.

This is a requirements omission rather than a dependency problem or a deviation from the present artifacts. The desired hacking animation must first be encoded across the spec, design model, plan, and tasks before implementation is changed.
