# Data Model: Player Sessions, Character Assignment, and Shared Terminal Control

All entities in this document are process-local unless explicitly identified as an existing durable authored model. None is added to version-1 session JSON.

## ProcessRuntime

`ProcessRuntime` is the private root owned by `internal/control.Service`.

| Field | Type | Rules |
|---|---|---|
| `Revision` | unsigned integer | Monotonically increases once for each accepted canonical transition; never supplied by a client. |
| `SessionsByID` | map of `LogicalSessionID` to `LogicalSession` | Retained until process restart. |
| `SessionIDByBrowserToken` | map of opaque token to `LogicalSessionID` | Private recognition index; token values never enter logs, URLs, master state, or player state. |
| `RosterByID` | ordered map of `CharacterID` to `CharacterRosterEntry` | Retained across broadcast endings; cleared on process restart. |
| `Broadcast` | optional `LiveBroadcast` | Nil when no broadcast exists. |
| `PendingSwitch` | optional `TerminalSwitchDecision` | At most one unresolved game-master terminal-switch request. |

Every mutation holds the coordinator mutex, validates against this root, updates it, produces detached effects, and enqueues those effects before unlocking. Returned and published maps, slices, trees, navigation values, and hacking values must not alias this root.

## BrowserRecognition

| Field | Type | Rules |
|---|---|---|
| `BrowserToken` | opaque string | Cryptographically generated by the running server, stored only in same-origin browser `localStorage`, and presented only in `SESSION_HELLO`. It is a continuity handle, not authentication. |
| `SessionID` | `LogicalSessionID` | Process-local mapping target. An unknown token creates a fresh token and fresh session instead of restoring state. |

The browser serializes a first-use handshake across tabs so only one token-issuing connection runs before the token is stored. A different origin, profile, private context, or cleared storage has no token mapping and establishes another session.

## LogicalSession

| Field | Type | Rules |
|---|---|---|
| `ID` | opaque `LogicalSessionID` | Unique for the server process; never reused. |
| `FallbackName` | string | Nonblank, unique among process sessions, automatically generated on creation, and mutable only by the game master. |
| `ConnectionIDs` | set of connection ID | Private membership; one or more means connected. Raw IDs are never included in player projections. |
| `RequestResults` | bounded map of `requestId` to request fingerprint plus `ActionResult` | Deduplicates current-broadcast requests from one or several tabs. An exact replay returns the original result; reuse with different fields is rejected as `duplicate`. Cleared when the broadcast ends. |

`Connected` is derived as `len(ConnectionIDs) > 0`. Assignment and role are resolved from the current `LiveBroadcast`, not stored as durable session fields. Closing one connection removes only that membership; the final removal changes presence but preserves assignment and controller identity.

## CharacterRosterEntry

| Field | Type | Rules |
|---|---|---|
| `ID` | opaque `CharacterID` | Stable and unique for the server process. |
| `Name` | string | Trimmed, nonblank, at most 80 Unicode code points; duplicate visible names are allowed. |

Availability is derived from the current broadcast's assignment index. Renaming retains identity and every existing claim. Deletion is rejected while the current broadcast claims the entry.

## LiveBroadcast

| Field | Type | Rules |
|---|---|---|
| `ID` | opaque `BroadcastID` | Fresh for each broadcast; stale selection and action requests must match it exactly. |
| `AssignmentsBySession` | map of `LogicalSessionID` to `CharacterID` | At most one character per session. |
| `SessionByCharacter` | map of `CharacterID` to `LogicalSessionID` | Inverse exclusive index; both maps change in one transaction. |
| `ControllerSessionID` | optional `LogicalSessionID` | Nil or one assigned session. May refer to a disconnected session. |
| `ActiveTerminalID` | optional durable terminal ID | Nil is a valid assigned-player waiting state and does not end the broadcast. |
| `TerminalRuntimes` | map of terminal ID to `TerminalRuntime` | Contains the active runtime and any explicitly preserved suspended runtimes. |

Ending the broadcast deletes this aggregate and every request-result cache, assignment, controller, active-terminal reference, pending switch, and terminal runtime. It does not delete `LogicalSession` or `CharacterRosterEntry` values.

## CharacterAssignment

`CharacterAssignment` is the exclusive relationship represented by both broadcast indexes.

| Field | Type | Rules |
|---|---|---|
| `BroadcastID` | `BroadcastID` | Prevents a claim from surviving or targeting another broadcast. |
| `SessionID` | `LogicalSessionID` | Unique within the broadcast assignment map. |
| `CharacterID` | `CharacterID` | Unique within the inverse claim map. |

Player selection succeeds only for an unassigned current session and an available current roster entry. Game-master assignment follows the same exclusivity rules. Release removes both indexes. Move removes the character from its old session and installs it on one unassigned destination as one transition. Releasing or moving the controller's character clears `ControllerSessionID` unless the same game-master command explicitly assigns another eligible controller.

## ControllerAssignment

`ControllerAssignment` is the optional `ControllerSessionID` reference in the current broadcast.

Validation invariants:

- The referenced session has a current assignment.
- At most one reference exists globally across every terminal.
- Game-master reassignment requires a connected assigned destination.
- Disconnect retains the reference; reconnect restores control if it was not reassigned.
- Existing observers are never elected due to disconnect, release, move, or terminal switching.
- A successful new eligible assignment may establish control only while no controller exists; moving the active character never transfers control implicitly.

## TerminalRuntime

| Field | Type | Rules |
|---|---|---|
| `TerminalID` | durable terminal ID | Key copied from the current authored terminal; not a new persisted field. |
| `TerminalName` | string | Latest validated authored display name applied at activation/update. |
| `Tree` | `ContentNode` | Detached latest authored tree. |
| `HackLevel` | integer | Level that created the retained puzzle. For a preserved unfinished puzzle it remains part of the exact checkpoint; a newer authored level applies only after discard/fresh generation. |
| `IntroText` | string | Latest validated authored text. |
| `Nav` | `NavState` | Existing canonical shared navigation. |
| `Hack` | optional private `HackState` | Complete canonical puzzle including secrets, candidates, generation identity, used patterns, attempts, board, log, and outcome. |
| `Lifecycle` | `active` or `suspended` | Exactly one runtime may be active; suspended runtimes reject all player actions. |

Preserve changes the current runtime from active to suspended without copying through a public representation. Reactivation reapplies the latest authored name, tree, and intro text; existing navigation is revalidated against the new tree and the private puzzle, including its generation level, is retained exactly. The latest authored hack level is used only when no preserved puzzle exists and a fresh runtime is generated. Discard removes the runtime so a later activation creates fresh navigation/puzzle state under existing rules.

## TerminalSwitchDecision

| Field | Type | Rules |
|---|---|---|
| `ID` | opaque `SwitchID` | Issued only when leaving the current active terminal requires a decision. |
| `BroadcastID` | `BroadcastID` | Resolution is rejected after broadcast end/restart. |
| `SourceTerminalID` | terminal ID | Must still be the active terminal at resolution. |
| `Target` | optional validated authored terminal payload | Nil means clear the active terminal while keeping the broadcast alive. |

Allowed decisions are `preserve`, `discard`, and `cancel`. While pending, the source terminal remains active and player actions continue in normal coordinator order. Cancel removes only the decision. Preserve or discard is revalidated against the current source state, performs the chosen source transition, activates or clears the target, and publishes one ordered result. If another privileged lifecycle command invalidates the source or broadcast first, resolution is rejected as stale.

## RuntimeCommand and ActionResult

Player-originated shared commands contain:

| Field | Type | Rules |
|---|---|---|
| `RequestID` | opaque client-generated string | Required, nonblank, and unique per logical session/broadcast; an exact duplicate returns the cached result, while reuse for a different payload is rejected. |
| `BroadcastID` | opaque string | Required for selection and terminal actions; must equal the current broadcast. |
| `TerminalID` | terminal ID | Required for navigation and hacking actions; must equal the active terminal. |
| action fields | type-specific values | Existing navigation action/node, guess target, or opaque pattern identity. |

`ActionResult` contains `RequestID`, `Accepted`, stable `Reason`, and the coordinator `Revision` observed after processing. An accepted result is delivered after the corresponding detached state effects have been enqueued. A rejected result changes no canonical gameplay state and uses the current revision. The client clears accepted pending input after applying the required projection at or beyond that revision, and clears rejected pending input immediately on the correlated result.

Stable rejection reasons are `invalid-session`, `stale-broadcast`, `unassigned`, `not-controller`, `controller-disconnected`, `stale-terminal`, `invalid-action`, `conflict`, and `duplicate`. Public reasons describe eligibility only and disclose no private connection or hacking facts.

## MasterCoordinationState

The private Wails projection is one detached revision:

- `revision`;
- process-local roster entries with claim status;
- all recognized logical sessions with fallback name, connected presence, character identity/name when assigned, and `active`, `observer`, or `unassigned` role;
- optional broadcast ID, controller session ID, active terminal ID, and pending switch metadata.

This projection may associate session and character IDs for game-master correction. It excludes browser tokens, raw connection IDs, private hacking data, request-result caches, and canonical mutable references.

## PlayerState

The personalized browser projection contains:

- `revision`;
- own `sessionId` and `fallbackName`;
- own assigned character ID/name when any;
- own role: `unassigned`, `active`, or `observer`;
- optional current `broadcastId` and `activeTerminalId`;
- phase: `no-broadcast`, `selecting`, `waiting`, `controlling`, or `observing`;
- roster entries with only `id`, `name`, and `available` or `claimed` status.

After assignment, character name is the primary displayed identity and fallback name remains a secondary technical label. Player state excludes other sessions, claimant identity, presence details, browser tokens after welcome, raw connections, and all private hacking fields.

## Relationships

```text
ProcessRuntime 1 ── * BrowserRecognition * ── 1 LogicalSession
ProcessRuntime 1 ── * LogicalSession
ProcessRuntime 1 ── * CharacterRosterEntry
ProcessRuntime 1 ── 0..1 LiveBroadcast

LiveBroadcast 1 ── * CharacterAssignment
CharacterAssignment * ── 1 LogicalSession
CharacterAssignment * ── 1 CharacterRosterEntry
LiveBroadcast 1 ── 0..1 ControllerAssignment ── 1 LogicalSession
LiveBroadcast 1 ── * TerminalRuntime
ProcessRuntime 1 ── 0..1 TerminalSwitchDecision
```

## State Transitions

### Session and Presence

```text
HELLO with known token
  → attach connection to mapped logical session
  → first connection changes presence to connected
  → send SESSION_WELCOME and current personalized state

HELLO with absent or unknown token
  → issue replacement token + fresh logical session/fallback name
  → attach connection and return SESSION_WELCOME

connection closes
  → remove only that membership
  → more memberships remain: presence unchanged
  → final membership removed: mark disconnected; keep claim/controller
```

### Selection and Controller Establishment

```text
validate session + requestId + broadcastId + available character
  → atomically install both assignment indexes
  → controller exists: new assignment is observer
  → no controller: eligible new assignment becomes controller
  → publish player/master states and ACTION_RESULT
```

Concurrent claims and concurrent first assignments serialize under the same mutex, so only one conflicting claim and only one initial controller can commit.

### Player Action

```text
resolve sending connection → logical session
  → deduplicate requestId
  → require current broadcast + assignment + controller + connected presence
  → require request terminal == active terminal
  → invoke existing nav/hack rule under the same coordinator transaction
  → enqueue canonical terminal projection(s)
  → cache and enqueue ACTION_RESULT
```

Any failed precondition exits without navigation, puzzle, attempts, randomness, logs, outcomes, or terminal mutation.

### Terminal Switch

```text
request target/clear
  → no unfinished active puzzle: activate/clear directly
  → unfinished puzzle: create decision; keep source active

resolve cancel
  → remove decision only

resolve preserve
  → suspend exact source runtime
  → activate target runtime (restore if preserved, otherwise create) or clear active target

resolve discard
  → delete source runtime
  → activate target runtime (restore if preserved, otherwise create) or clear active target
```

### Broadcast End and Restart

```text
end broadcast
  → clear claims/controller/active terminal/pending switch/runtime slots/request caches
  → retain logical sessions/fallback names/roster

start new broadcast
  → issue fresh broadcast ID
  → every session is unassigned; controller nil

server process restart
  → discard complete ProcessRuntime
  → any presented old browser token is unknown and creates a fresh session/token
```

## Persistence Boundary

The existing version-1 JSON remains limited to campaign name and authored terminals with ID, name, hack level, intro text, and content tree. It gains no browser token, logical session, fallback name, connection, presence, roster, claim, assignment, role, controller, broadcast ID, active terminal, revision, request result, pending switch, suspended terminal, navigation, puzzle, attempts, board, patterns, log, or outcome field.
