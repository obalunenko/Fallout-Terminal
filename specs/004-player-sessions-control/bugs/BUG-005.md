## Description

After players exhaust the shared hacking attempts, the player surface remains on the blocked screen and the game-master status reads `ВЗЛОМ: ЗАБЛОКИРОВАН (нужен перезапуск трансляции)`. The game master has no action that discards the failed puzzle and creates a fresh puzzle for the same active terminal, so players cannot retry while the current broadcast, character claims, and controller assignment remain intact.

The only available recovery is to end and start the entire broadcast. That workaround clears the broadcast epoch, character claims, controller assignment, active terminal, and runtime slots, forcing every recognized player to select a character again. The trusted `ForceHackSuccess` action cannot recover the table after lockout because it is intentionally disabled for failed puzzles.

The migrated hacking contract requires failure to block navigation until the live terminal is restarted and requires that restart to generate a fresh server-owned puzzle. The current coordination contract changed `StartBroadcast` into a whole-broadcast lifetime boundary, treats activation of the already-active terminal as a content update that preserves its puzzle, and exposes discard only while switching away from an *unfinished* puzzle. Consequently, no current game-master command implements the established same-terminal retry boundary.

## Root Cause Analysis

This is implementation drift enabled by an untested cross-feature recovery flow. The original hacking specification intentionally made a fresh live-terminal start/restart the boundary that replaces a failed puzzle. The player-sessions feature later separated the broadcast epoch from active-terminal runtime, correctly preserved terminal puzzles across updates and reactivation, and restricted `ForceHackSuccess` to unfinished puzzles. However, it modeled discard only as a decision during a switch away from an unfinished puzzle and made activating the current terminal a non-resetting update.

Those individually valid rules leave a state-machine hole at `active terminal + failed puzzle`: player actions are rejected, forced success is disabled, same-terminal activation preserves failure, clear/reactivate preserves the runtime, and discard cannot be requested. Only `EndBroadcast` deletes the failed runtime, but it also deletes unrelated claims and controller state. Because tests cover lockout, unfinished switching, and broadcast end/start separately, all can pass without proving that the game master can let the same table retry after failure.

## Resolution

Implemented as T139–T144. The trusted `ResetFailedHack` transition now replaces only the current failed active terminal runtime from the latest validated authored settings, emits one ordered fresh projection to assigned active and observer sessions, restores full attempts, and keeps the broadcast, terminal identity, assignments, controller, roster, sessions, other runtime slots, and durable state intact. The master blocked state exposes `ПОВТОРИТЬ ВЗЛОМ`; player transports expose no reset authority. Generation-scoped candidate and pattern identities reject delayed actions from the discarded puzzle.

Verification passed: format, vet, full Go and race suites, frontend production build, 30/30 Playwright journeys, Wails production package, and a packaged native active/observer failed-to-fresh retry journey. Detailed evidence is recorded in `validation.md` under **BUG-005 failed-hack retry regression** and SC-030/SC-031.
