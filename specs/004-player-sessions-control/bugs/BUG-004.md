# Bug Report: End Broadcast Button Does Not Stop Player Broadcast

**Type**: Implementation drift
**Severity**: High
**Feature**: `004-player-sessions-control` — Player Sessions, Character Assignment, and Shared Terminal Control
**Reported**: 2026-08-12
**Status**: Patched
**Patched**: 2026-08-12

## Description

During an active broadcast, the game-master button labeled `ЗАВЕРШИТЬ ТРАНСЛЯЦИЮ` cannot be used successfully. It appears unavailable or produces no observable result when pressed, and the currently active terminal remains broadcast to player clients.

The expected behavior is that pressing the button invokes the trusted `EndBroadcast` command, ends the current broadcast epoch, removes the active terminal from every player, clears all current character claims and controller assignment, and moves connected players to the appropriate no-broadcast waiting state while retaining recognized logical sessions, fallback names, the authored roster, and configured durable terminals.

The lower layers already contain `desktopAPI.endBroadcast()`, `App.EndBroadcast()`, coordinator cleanup, and player clear/context publication. The master handler also exists, but it is not covered as one executable interaction. It first checks local pending/broadcast state and then calls `window.confirm`; only after confirmation does it invoke the desktop command. The current tests prove the coordinator, App, server fanout, and player reaction separately, but no test starts from an actual click on `#btnEndBroadcast` and proves that the call reaches players. The exact first failing boundary — disabled/obstructed button state, confirmation handling in the Wails webview, desktop-facade invocation, returned state application, or publication — must be reproduced before selecting the fix.

## Root Cause Analysis

This is implementation drift combined with an untested composed interaction. The requirements, model, contract, coordinator, App method, desktop facade, and player-side lifecycle response all describe the intended behavior, and isolated tests cover most of those layers. However, the master browser path is only present as source code: the Playwright US9 journey injects `PLAYER_STATE` directly into the player client, and the recorded native validation stops at launch/render rather than clicking the end-broadcast control.

Consequently, all automated suites can pass while the real user action remains unavailable. `window.confirm` is a unique, untested gate in this handler and is one investigation point, but the current evidence does not establish it as the root cause. The first failing boundary must be captured with a real or production-shaped master interaction before changing code.
