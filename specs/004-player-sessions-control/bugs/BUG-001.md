# Bug Report: Player Roster Is Lost Between Session Uses

**Type**: Spec conflict
**Severity**: Medium
**Feature**: `004-player-sessions-control` — Player Sessions, Character Assignment, and Shared Terminal Control
**Reported**: 2026-08-12
**Status**: Patched
**Patched**: 2026-08-12

## Description

Player/character entries added by the game master are kept only in the running process. After the application restarts, the game master must enter the same roster again even when reopening the same campaign session file.

The durable configuration associated with a campaign session must provide a reusable player roster. One proposed workflow is to keep player data in a separate player-config file: after the game master creates or opens a session config, the application offers to select an existing player config or create a new one. The selected association and roster must be recoverable on a later use so routine setup does not require manual re-entry.

This report treats “players/users” as the game-master-authored roster entries and their stable roster identities. Browser recognition tokens, live logical connections, presence, current-broadcast claims, controller assignment, active terminal, and puzzle state remain runtime data unless a later patch explicitly broadens the persistence requirement.

The current artifacts deliberately specify the opposite behavior: the roster is process-local, is cleared on restart, and is prohibited from entering the persisted version-1 session JSON.

## Artifact Traceability

### spec.md

- **Affected user stories**:
  - **User Story 4 — Manage Roster and Assignments**: the game master can add and maintain roster characters, but the story has no reopen/restart recovery scenario.
  - **User Story 9 — End and Restart Broadcast Lifetimes**: Acceptance Scenario 4 requires prior runtime state to disappear after restart, without distinguishing reusable authored roster configuration from transient logical sessions and claims.
- **Affected requirements**:
  - **FR-011** requires logical-session identity and fallback-name changes to remain process-local. This should continue for browser/runtime identity, but the requirement currently leaves no durable game-master-authored player identity.
  - **FR-018** prohibits runtime session and coordination data from being added to the version-1 session schema. A patch must distinguish the reusable roster/config reference from the prohibited transient values.
  - **FR-019–FR-022** define game-master roster creation, stable identity, add, and rename behavior only within the current process and omit persistence, selection, creation, and reload behavior for a player config.
  - **SC-019** requires restart to restore no prior logical session or claim, but does not verify that an authored roster can be recovered independently.
  - **SC-020** explicitly verifies that roster data is absent from version-1 persistence, conflicting with the reported expectation unless a separate durable player-config contract is introduced.
- **Gap/conflict identified**: The spec conflates authored roster configuration, which the game master expects to reuse, with transient browser sessions, presence, claims, and controller state, which should expire. It also lacks a startup/open-session workflow for selecting, creating, remembering, canceling, validating, or replacing a player config.

### plan.md

- **Affected sections**:
  - **Summary**: states that all roster state is process-local and that durable version-1 session JSON remains unchanged.
  - **Project Structure / Structure Decision**: places the roster only in `internal/control` and explicitly separates it from durable session storage.
  - **Constitution Check, Principle IV**: treats process-local roster entries and absence of any migration as the required compatibility outcome.
  - **Implementation Strategy 1 and 4**: keep durable models unchanged and clear the roster on process restart.
  - **Implementation Strategy 10–12**: expose roster operations only through runtime coordination and test restart cleanup rather than roster restoration.
  - **Verification Gates**: require no roster field in version-1 JSON.
- **Impact**: Planning must introduce an explicit durable boundary for authored roster configuration without persisting live coordination state. It must choose and document either an evolved session schema or a separate player-config file plus session-to-player-config association, native select/create/cancel/error behavior, load order after session selection, validation, atomic writes, compatibility for sessions with no player config, and tests across restart/reopen.

  - **T047** explicitly verifies roster/assignment commands make no durable session-saving calls.
  - **T050–T057** implement complete roster management only through runtime coordination state.

  - Add the game-master flow that offers “select existing player config” or “create new player config” after session creation/opening, while supporting sessions that do not yet have one.

### research.md

- **Affected decisions**:
  - **Decision 2** rejects persisting server logical sessions in campaign JSON; that remains appropriate for runtime browser identity but does not address authored roster persistence.
  - **Decision 3** places roster entries at process scope and clears them on restart.
  - **Decision 8** rejects a durable store because all new state was assumed to expire at process or broadcast boundaries.
- **Impact**: Research must supersede the assumption that every roster value is runtime-only. It should compare an embedded session-schema change with a separate player-config file, then define ownership, portability, missing-file recovery, validation, save ordering, and privacy boundaries for the selected design.

### data-model.md

- **Affected sections**:
  - **ProcessRuntime** stores `RosterByID` only until restart.
  - **CharacterRosterEntry** has process-stable identity but no durable representation.
  - **Broadcast End and Restart** discards the complete process runtime on restart.
  - **Persistence Boundary** explicitly excludes the roster from version-1 session JSON.
- **Impact**: The model needs a durable authored roster/player-config entity and a load-time association with the campaign session, while retaining a separate runtime projection for availability and claims. Persisted data must exclude browser tokens, connection IDs, presence, assignments, controller state, broadcasts, revisions, requests, active/suspended terminals, navigation, and puzzles.

## Root Cause Analysis

The missing behavior is not implementation drift. The feature intentionally classified roster entries together with other coordination data as process-local, and the plan, data model, implementation tasks, and regression tests consistently enforce that decision. The new report reveals that authored player names are campaign setup data with a longer lifetime than live connections and claims. The original lifetime model did not separate reusable roster configuration from transient coordination state, so no persistence contract or load UX was planned.

## Recommended Fix

1. Run `/speckit.bugfix.patch BUG-001` to separate durable roster configuration from transient player-session state across spec, plan, research, data model, contracts, and tasks.
2. During the patch, formalize the proposed separate player-config workflow (or explicitly choose an evolved session schema), including how the association is remembered and what happens on cancel, missing files, invalid files, and first use.
3. Run `/speckit.bugfix.verify BUG-001` to confirm the persistence boundary and restart behavior are consistent across all artifacts.
4. Resume `/speckit.implement` to add the storage boundary, selection/create UI, autosave/update behavior, compatibility handling, and regressions.
