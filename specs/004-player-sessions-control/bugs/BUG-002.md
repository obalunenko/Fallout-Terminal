# Bug Report: New Player Config Cannot Install an Empty Roster

**Type**: Implementation drift
**Severity**: High
**Feature**: `004-player-sessions-control` — Player Sessions, Character Assignment, and Shared Terminal Control
**Reported**: 2026-08-12
**Status**: Patched
**Patched**: 2026-08-12

## Description

When the game master creates a new player-config file, the application reports `roster must be an array` instead of associating and activating the newly created empty configuration.

The file creation boundary initially constructs and writes a valid version-1 document with `"roster": []`. During the same create-and-install workflow, however, the empty non-nil Go slice is cloned with an append whose destination is nil. That clone produces a nil slice. The coordinator repeats the same nil-destination clone before calling strict player-config validation, so validation rejects the just-created in-memory configuration even though the file written to disk contains the required empty JSON array.

The failure blocks the primary first-use path: the standalone player-config file may be created successfully, but it is not installed as the active configuration and its association with the session cannot complete.

## Root Cause Analysis

The specification, plan, research, and data model consistently require an empty roster array for a new player config. The defect is implementation drift combined with an untested representation edge case.

`playerconfig.Service.Create` correctly constructs `Roster: []domain.CharacterRosterEntry{}` and writes a valid JSON array. The service result then calls `cloneRoster`, implemented as `append([]domain.CharacterRosterEntry(nil), roster...)`; for a zero-length input this returns nil. `control.Service.InstallPlayerConfig` performs the same nil-destination append and passes the resulting `PlayerConfig` to `ValidatePlayerConfig`, which correctly rejects nil with `roster must be an array`.

Existing tests assert only `len(created.Config.Roster) == 0` and use mocked boundaries that do not run the real empty roster through both clone points. Because both nil and an allocated empty slice have length zero, all automated gates passed while the real native workflow remained broken.

## Recommended Fix

1. Run `/speckit.bugfix.patch BUG-002` to reopen or supersede the affected tasks and add explicit empty-array preservation and end-to-end regression coverage.
2. Preserve non-nil empty roster slices at every clone boundary, while retaining strict rejection of missing or `null` roster values during decoding and validation.
3. Add the real `NewPlayerConfig` integration regression and rerun `/speckit.bugfix.verify BUG-002`.
4. Resume `/speckit.implement` to apply and validate the code fix.
