# Bug Report: Hacking Outcome Sounds Do Not Play for Player

**Type**: Implementation drift
**Severity**: Medium
**Feature**: `004-player-sessions-control` — Player Sessions, Character Assignment, and Shared Terminal Control
**Reported**: 2026-08-12
**Status**: Patched
**Patched**: 2026-08-12

## Description

On the player hacking-password screen, moving the cursor over rendered characters still plays the local hover/cursor sound. Selecting a password variant, however, produces no outcome sound when the selection is wrong, when the correct password unlocks the terminal, or when the final wrong selection locks the terminal.

The canonical hacking transitions and visual state may still arrive, but their established player audio feedback is absent. The expected behavior is that an authoritative wrong-selection transition plays the bad-guess cue, a newly solved transition plays the good/unlock cue, and the final wrong-selection transition that changes the puzzle to failed plays the applicable bad/lockout cue. Each cue must play once for the applied transition and must not be triggered optimistically by the click before the server outcome arrives.

## Root Cause Analysis

This is implementation drift enabled by an untested cross-feature presentation flow. The original hacking artifacts explicitly implemented incorrect-guess and correct-guess audio and require success audio when the solved state arrives. The player-sessions feature then moved shared actions behind role gating, revision checks, personalized state, coordinator publication, and correlated completion while promising to preserve existing sound behavior.

The current client still contains `playHackBad()` and `playHackGood()` calls in its `HACK_STATE` handler and the corresponding sound assets exist, so the report does not yet establish whether the first failing boundary is transition detection, revision/message ordering, sound-folder readiness, Web Audio decoding/resume, or packaged-runtime playback. What is established is that existing tests cannot detect the reported failure: browser fixtures replace `HTMLMediaElement.play` but do not observe Web Audio buffer playback or assert bad/good cue invocation, and asset tests prove only that sound files and categories are present. Thus the composed player journey can pass while all authoritative hacking outcome cues are inaudible.
