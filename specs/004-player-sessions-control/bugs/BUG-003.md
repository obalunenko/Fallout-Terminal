## Description

The logical session currently designated as the active controller cannot select interactive elements while solving the hacking game. Password candidates, filler cells, and special-pattern openings are presented on the board, but selecting a target does not perform the active player's expected hacking action.

This blocks the only player session authorized to advance the puzzle. Observers are intentionally read-only, but the active controller must be able to submit the existing `HACK_GUESS` and `HACK_PATTERN` actions and receive the authoritative shared result. The report is limited to target selection during an active hacking puzzle; the exact behavior of keyboard-only input and the precise failing boundary still require reproduction through the fully composed application.

## Root Cause Analysis

The specification and design explicitly require the active controller to select hacking targets, and the implementation contains isolated tests for browser click handling, WebSocket dispatch, coordinator authorization, and hacking mechanics. The observed failure therefore indicates integration drift across those boundaries rather than a missing product requirement.

Current browser hacking tests inject `role: active`, `phase: controlling`, and terminal snapshots through a fake WebSocket. Coordinator tests invoke runtime commands directly, while socket tests use coordinator seams. These tests can all pass without proving that the production composition delivers a mutually consistent active role, terminal mirror, DOM target, outbound request, accepted mutation, state revision, and pending completion to the same real browser session. The exact defective boundary must be established by the composed reproduction before changing code; likely investigation points are client-side authority/pending gating, personalized state and live-snapshot ordering, target-to-request mapping, sender/session binding, and action-result revision delivery.
