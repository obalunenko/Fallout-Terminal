**Type**: Implementation drift

## Description

On the player password-hacking screen, the CRT ambient loop and character-scroll reveal sound play, but no other expected hacking-screen sounds are audible. This includes the established target-preview tones for individual and grouped targets, the selection/entry cue, and the authoritative bad-guess and good/unlock outcome cues. The final wrong guess that locks the terminal is also expected to use the bad cue.

This report is broader than BUG-006. BUG-006 assumed cursor/click sounds were working and restored only authoritative wrong, unlock, and lockout playback. The newly reported runtime behavior contradicts that premise: only ambient and character-scroll audio are heard, while the remaining hacking interaction and outcome sound families are silent. Canonical hacking actions and visual state may still complete normally.

The exact silent families must be reproduced on the real player surface after one user gesture. `menu-focus` belongs to normal terminal navigation and is not asserted as a password-screen cue by this report.

## Root Cause Analysis

This is implementation drift with an incomplete production-audio verification boundary. The code still declares and calls `playSingle`, `playMultiple`, `playEnter`, `playHackBad`, and `playHackGood`, all corresponding sound folders contain non-empty WAV assets, and the player HTTP allowlist includes every family. Those facts establish intended wiring and packaged presence, not audible execution.

The current browser regressions replace the browser's native `AudioContext` with a fake implementation whose `decodeAudioData()` always succeeds and whose `start()` increments a counter. The optional playback observer is called after that synthetic source start. This can prove that a logical URL reached the adapter under the fixture, but it cannot prove that the real browser decoded the selected asset, routed it to an actual output device, or produced audible sound. The BUG-006 validation records source starts in headless Chromium documents, so its packaged evidence likewise does not establish human-audible output.

The working character-scroll sound is important counter-evidence against a blanket autoplay or Web Audio failure because it uses the same Web Audio adapter. The first failing boundary may instead vary by event family, manifest readiness, selected asset, native decoding, context timing, or output routing. The report does not establish which of these is causal; the correction must follow a reproduction that observes each boundary on the real player surface.
